# RealmCraft Companion first comprehensive code audit

Audit date: 2026-09-07  
macOS version: 1.7.35, build 57  
Android version: 0.9.0, versionCode 12, Git base `1f045a45f364551fcae1155777c1f82d821edacb`; the audited worktree also contains uncommitted development changes  
Web version: 0.4.1 as documented locally; no local Git metadata

## Outcome

The project has a substantial, safety-conscious macOS core with 18 user-facing destinations, conservative save readers and unusually broad synthetic regression coverage. The new layer-analysis and Nether-metro ideas can reuse the existing decoder, map renderer, coordinate transforms, overlays, portal records and navigation export. They should not start as parallel map/parser implementations.

The main structural risk is orchestration: map tools and metadata stores grew feature by feature, so selection state, persistence scope and cross-platform format behavior are fragmented. The audit found one failing regression test, one unsafe default build destination after the app symlink change, and clear documentation/backlog drift. No evidence was found that the shipped app currently modifies saves outside the explicit editor/restore flows.

## Findings

### P1 — Default build can replace the installed app

`build.sh` defaults `REALMCRAFT_APP_OUTPUT` to `../RealmCraft Companion.app`. The project-level path is now a symlink to `/Applications/RealmCraft Companion.app`, so the documented plain `./build.sh` command writes into the installed bundle. The script also copies resources into the destination without first creating a fresh bundle, allowing removed resources to remain when an existing app is reused.

Impact: an ordinary development build can unexpectedly replace the working installation and may retain stale resources. This conflicts with the project rule requiring a separate temporary bundle first.

Evidence: `build.sh` (`APP` default and resource copy); project app symlink documented in the root project instructions.

Required fix: default to a new temporary build bundle or require an explicit destination, reject symlink/existing installed targets unless an explicit install mode is selected, and verify the produced temporary app before a separate install step.

### P1 — Atlas regression gate is red after portal integration

Running all embedded-atlas Node tests produced 56 passes and one failure. `Tests/orientation.test.cjs` evaluates `app.js` with stubs but neither loads `portals.js` nor supplies `AtlasPortals`. `app.js` now constructs `AtlasPortals.Planner`, raising `ReferenceError: AtlasPortals is not defined` before the test assertions.

Impact: the complete Node regression command is unusable as a green gate and can hide later orientation/map failures. The production `index.html` does load `portals.js` before `app.js`, so this audit does not classify it as a proven application runtime failure.

Evidence: `Tests/orientation.test.cjs` lines 17–19; map `app.js` line 42; map `index.html` lines 45–61.

Required fix: include the real portal module in the harness or add a behaviorally sufficient planner stub, then rerun the full atlas suite.

### P2 — Android public status and backlog contradicted current code (resolved in audit)

Android `app/build.gradle` declares 0.9.0/versionCode 12, while the checked-in `README.md` still says “Status: 0.1.1” and names a 0.1.1 APK. Its backlog still asks for byte progress/cancellation/free-space guidance and snapshot ZIP export even though the 0.8.0 changelog/source document those capabilities.

Impact before correction: testers could download or sideload the wrong artifact and contributors could duplicate completed work.

Evidence: Android `app/build.gradle` lines 11–12; `README.md` lines 5 and 12; `BACKLOG.md` lines 15 and 17; `CHANGELOG.md` 0.8.0.

Resolution in this audit: aligned the README with 0.9.0 and marked the two shipped backlog items complete without deleting their history. Unrelated Android worktree changes were not modified.

### P2 — New map tools share concepts but not one coordinator

Ownership, measurement, route generation and portal planning each manage their own active state, selected points and cancellation behavior. `app.js` wires mutual cancellation through callbacks. The pattern works for current tools but adding area-based layer analysis or metro-edge editing would add another competing state machine.

Impact: tool conflicts, stale selections and rotation/dimension bugs become increasingly likely; duplicated UI logic obscures reuse.

Evidence: map `measure.js` (`Measure`), `ownership.js` (`AtlasOwnership`), `portals.js` (`Planner`), `navigation.js` (`install`) and construction in `app.js` lines 32–42.

Required design: a shared tool coordinator plus typed point/rectangle/path selections in world coordinates, with activation, Escape, dimension-change and privacy policies tested once.

### P2 — Planning persistence scope is inconsistent

Markers, names and chest ownership use `Savegame.annotationScope`, which can be copied forward between snapshots. Portal plans and observed pairs are stored by save UUID. Ore journals are grouped by logical world. A future metro network would therefore have no clear lifetime.

Impact: a newly imported backup can appear to lose planning metadata, or a future implementation may accidentally combine evidence from incompatible snapshots.

Evidence: `Savegame.annotationScope` in `Library.swift`; scoped keys in `MapsView.swift`; `.portal-plans/<saveID>.json` and `.portal-pairs/<saveID>.json`; `OreJournal.directory` keyed from world ID.

Required decision: define snapshot, logical-world and global metadata ownership before introducing metro nodes/edges. Preserve source snapshot/fingerprint evidence even if plans follow a logical world.

### P2 — Binary format knowledge is replicated without a common contract suite

The version-9 chunk, player, chest and sign rules are independently implemented in macOS Swift/Python, Android Java and web JavaScript. Each platform has good local tests, but the audit found no single fixture/expected-output package executed by every implementation.

Impact: a valid parser fix or newly verified record can drift across platforms while local suites remain green.

Evidence: Python `chunks.py`, `chests.py`, `signs.py`; Swift player/chest models; Android `FeatureReadersTest` and readers; web `save-reader.js` and tests.

Required design: canonical synthetic binary vectors and neutral expected JSON, versioned by observed save format, imported by every platform suite.

### P3 — Maintenance documentation was fragmented

The project had detailed README, Help, Backlog, Changelog and parity reports, but no central feature map, architecture/data-model documents or stable-ID comparison for the 2026-09-07 ideas. This caused historical text and current capability statements to coexist without an authoritative index.

Resolution in this audit: added `docs/FEATURE-MAP.md`, `docs/ARCHITECTURE.md`, `docs/DATA-MODEL.md` and `docs/IDEAS-2026-09-07.md`; linked prioritized follow-up work from the existing backlog.

Remaining gap: `package_source.py` does not select `docs/`, so public source packaging needs an explicit reviewed decision.

## Reuse conclusions

- Layer analysis should be an extension of `ores.scan`/`chunks.decode`, not of inventory/chest totals and not a new JavaScript binary decoder.
- The embedded atlas already solves rotated/mirrored world-coordinate display, vertical slices, block lookup and concurrent overlays.
- `OreScan` already carries the correct unknown/missing/error semantics and per-height totals. Generalize its aggregate contract carefully rather than discarding it.
- Portal blocks, directed observations and plans already have separate models. Keep those evidence states separate in a metro graph.
- Navigation already emits terrain-aware steps and mixed movement modes. Metro work should become another route graph/input only after portal mechanics are verified.
- Android and web should port capability contracts and fixtures after the macOS reference stabilizes; their read-only safety boundaries remain intentional.

## Nether Metro implementation addendum

The first safe increment adds a snapshot-local metro graph in `Sources/MetroModels.swift` and a macOS planning view in `Sources/MetroView.swift`. Stations have a dimension and world coordinates; lines have a name/color; edges are directed rail, portal or walking records. The model enforces same-dimension rail/walk edges and cross-dimension portal edges, but deliberately does not calculate a counterpart coordinate or infer a reverse route.

Shared interfaces deliberately reused: the existing `o`/`n` dimension identifiers and world-coordinate bounds, `CompanionFeature` sidebar composition, and the existing route-writing style of `NavigationPack`. The metro increment does not alter `PortalModels`, `PortalPlans`, `MapsView`, the Atlas JavaScript runtime, the ore census or their persistence contracts. Changed implementation files are `Sources/MetroModels.swift`, `Sources/MetroView.swift` and the narrow sidebar registration in `Sources/CompanionView.swift`; `Tests/MetroModelsTests.swift` is synthetic-only.

The schematic diagram is derived from the same records and explicitly uses alphabetical placement rather than a geographic projection. A copied turn-by-turn briefing is available only when every included station and directed edge is manually marked confirmed and every edge has a measured duration. Planned and built connections remain visible but are rejected by routing.

Portal verification is still incomplete: the documented matrix has no controlled RealmCraft evidence for scale, search radius, height, tie-breaking or reverse linking. The existing 8:1 implementation remains an unverified calculator and was not reused by metro routing. `Tests/MetroModelsTests.swift` supplies synthetic validation for evidence gating, directed routing, persistence and dimension rules; it cannot establish game mechanics.

Open dependencies: a controlled isolated-demo portal evidence matrix, a deliberate snapshot-versus-logical-world migration policy, a shared map-tool coordinator before geographic overlay editing, and a dimension-aware extension to `NavigationPack` before terrain walking and a metro journey can be exported as one route.
